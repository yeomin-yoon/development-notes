vector에 원소를 추가한 뒤 기존 참조를 써도 될까

2026년 10월 15일

문제 상황

게임의 아이템 목록을 std::vector로 관리한다.

현재 아이템은 두 개다. 아래 두 문제는 각각 이 목록에서 시작한다. 모든 코드는 한 Thread에서 실행되고, 출력 함수는 목록을 변경하지 않는다.

1. 선택한 아이템의 수량을 늘리려고 한다

첫 아이템을 선택해두고, 새 아이템을 추가한 뒤 선택한 아이템의 수량을 늘린다.

실행 전 상태가 다음과 같을 때, 이 코드는 안전할까?

A와 B를 판단하고, 두 경우 모두 아이템 100의 수량이 2가 되도록 수정해라.

2. 추가하기 전에 있던 아이템만 출력하려고 한다

이번에는 size = 2, capacity = 8이다.

끝 위치를 저장해두고 새 아이템을 추가한다. 그 뒤 저장한 끝 위치까지 출력한다.

이 코드는 안전할까? 아이템 100과 200만 출력하도록 수정해라.

풀이 — 생각을 마친 뒤 열기

1. 원소를 추가한 뒤 포인터를 얻으면 되지 않을까?

1. 원소를 추가한 뒤 포인터를 얻으면 되지 않을까?

처음에는 push_back({300, 1})을 “1을 300개 추가한다”로 읽었다. 실제로는 구조체의 필드 순서대로 ID 300, 수량 1인 Item 하나를 추가한다. size는 1 증가한다.

그다음에는 두 상태를 직접 구분했다.

“A는 안전하고 B는 안전하지 않다. B는 두 개에 하나를 추가하니 재할당되고, 기존 주소를 가리키던 포인터가 문제 된다.”

Selected는 “0번 인덱스”가 아니라 주소를 얻을 당시의 원소 위치를 저장한다. 재할당돼도 새 주소로 자동 갱신되지 않는다.

무효화된 포인터로 Selected->Count에 접근하면 정의되지 않은 동작이다. 크래시가 안 나더라도 안전한 코드는 아니다.

여기서 직접 수정 방향을 떠올렸다.

“push_back을 먼저 하고 Item* Selected = &Items[0];을 하면 되지 않나? 재할당 후에 얻으면 문제 없잖아.”

이번 조건에서는 A와 B 모두 해결된다. 끝에 추가해도 기존 첫 아이템은 100이며, 포인터를 얻은 뒤에는 vector를 변경하지 않는다. 포인터가 필요 없다면 Items[0].Count += 1;로 바로 접근해도 된다.

기존 원소의 참조와 iterator도 재할당되면 무효화된다. 반대로 재할당 없는 push_back에서는 기존 원소의 포인터·참조·iterator가 유지된다.

2. end도 추가한 뒤 다시 얻으면 되지 않을까?

2. end도 추가한 뒤 다시 얻으면 되지 않을까?

end()는 마지막 원소가 아니라 마지막 원소 바로 다음 위치다.

성공한 push_back은 재할당이 없어도 기존 end()를 무효화한다. 예전 end 위치에 새 원소가 생겼다고 해서, 저장한 iterator를 그 원소의 iterator로 사용해도 된다는 뜻은 아니다.

여기서도 직접 수정 방향을 제시했다.

“push_back 이전 end는 무효라서 문제인데, 이것도 push_back 이후에 얻으면 문제 없는 것 아닌가?”

새로 얻은 end는 유효하다. 다만 그 끝까지 출력하면 새 아이템 300도 포함된다. 안전성은 해결했지만 “기존 두 아이템만 출력한다”는 조건은 남았다.

“뒤에서 -1 하는 iterator가 있나?”라고 질문했고, vector iterator의 뺄셈을 확인했다.

Stop에 도착하기 전에 반복이 끝나므로 100과 200만 출력한다. 이번에는 정확히 하나를 추가했으므로 맞는 경계다. 빈 vector에서 end() - 1을 계산하면 안 된다.

기존 개수를 저장하는 방법도 함께 확인했다.

이 코드는 “원래 있던 개수만 출력한다”는 의도가 직접 보인다. 끝에 여러 개를 추가해도 사용할 수 있다. 중간 삽입이나 삭제가 섞이면 인덱스와 대상의 관계는 다시 확인해야 한다.

원인과 “변경 후 다시 얻기”는 직접 찾았다. 새 end까지 돌면 출력 범위가 달라진다는 점과, 범위를 맞추는 두 방법은 도움받아 완성했다.

insert / erase / reserve도 함께 기억하기

insert — 중간에 끼워 넣으면?

재할당이 없더라도 삽입 위치부터 뒤쪽의 기존 포인터·참조·iterator와 end는 무효화된다. 삽입 위치 앞은 유지된다. 재할당이 발생하면 전부 무효화된다.

erase — 중간 원소를 지우면?

삭제 위치부터 뒤쪽의 기존 참조·iterator와 end는 무효화된다. 삭제 위치 앞은 유지된다. 같은 자리에 데이터가 남아 있어도 예전 아이템을 계속 가리킨다고 가정하면 안 된다. capacity가 그대로라는 사실만으로 안전성을 판단하지 않는다.

reserve — 공간만 확보하면?

size는 그대로다. 요청한 수가 현재 capacity보다 크면 reserve 자체가 재할당을 일으킨다. 이때 기존 포인터·참조·iterator와 end는 전부 무효화된다. 현재 capacity 이하를 요청하면 재할당하지 않는다.

이후 추가로 size가 확보한 capacity를 넘기 전까지는 재할당되지 않는다. 중간 insert나 erase의 무효화까지 막는 것은 아니다.

실제로는 언제 이런 문제가 생길까?

이번 예제에서는 추가 후 포인터를 얻도록 순서만 바꾸면 해결됐다. 실제로는 포인터를 저장한 곳과 목록을 변경하는 곳이 떨어져 있을 수 있다.

잠깐 사용할 때는 필요한 변경을 마친 뒤 참조를 얻고, 사용하는 동안 무효화시키는 변경을 하지 않는다. 특정 아이템을 오래 기억해야 한다면 ID를 저장하고 사용할 때 다시 찾는 방법을 고려한다.

이번 문제의 핵심은 vector 변경 뒤에 저장한 포인터·참조·iterator를 계속 사용할 수 있는지 판단하는 것이다.
