그리드 반경 검색 정확성 검증

2026년 10월 19일

후보를 줄여도 같은 적을 찾았을까?

그리드는 적을 덜 검사하기 위한 구조다. 하지만 검사하지 않은 칸에 공격 대상이 남아 있다면 최적화가 아니라 누락이다. 이 실험은 검색 대상을 줄인 뒤에도 답이 같은지 확인했다. 시간은 측정하지 않았다.

순서는 달라도 된다. 다만 중복을 제거한 뒤 비교하지는 않는다. 중복 반환도 오류로 잡기 위해서다. 기준 전체 순회는 그리드의 칸 목록을 읽지 않는다.

거리 식은 같게 두었다. 따라서 결과가 다르면 먼저 그 적이 등록된 칸을 방문했는지를 확인할 수 있다. 작은 사례에서는 기대 ID도 직접 지정해 전체 순회 자체의 결과부터 확인했다.

어떤 조건을 확인했나?

조건확인한 의미
(3.9, 1) 주변의 (4.1, 1)다른 칸이어도 반경 안이면 누락하지 않는다
음수 좌표, 정확히 −4인 좌표음수 칸 번호와 경계 처리가 맞는다
사각형 모서리, 반경 경계와 그 직후사각형 안이어도 원 밖이면 제외하고, 거리 = 반경은 포함한다
반경 0, 빈 전장같은 위치만 포함하고 빈 목록도 처리한다
반경 10m, 칸 폭 4m고정된 주변 9칸 밖의 적도 찾는다
한 칸에 적 20,000명후보가 줄지 않아도 결과는 정확하다. 빠르다는 뜻은 아니다
칸 이동·같은 칸 내 이동·삭제·추가현재 위치와 생존 상태를 검색 결과에 반영한다

이렇게 기대하는 ID를 직접 지정한 조회가 14개다. 전체 순회의 결과부터 기대 ID와 같은지 확인한 다음, 수정한 그리드 결과와 비교했다.

추가로 적 20,000명에 대해 다음 조합을 확인했다.

좌표는 양수·음수를 포함하는 재현 가능한 데이터이며, 조회 반경은 0·2·10·40m를 사용했다. 변경 후에도 적 수는 20,000명을 유지했다.

각 적이 현재 칸에 정확히 한 번 등록되었는지, 삭제한 ID가 남아 있지 않은지도 별도로 검사했다.

잘못된 구현도 실제로 잡았나?

수정 코드만 통과하는 것으로 끝내지 않고, 일부러 오답 방식을 실행해 테스트가 누락을 잡는지도 확인했다.

일부러 실행한 방식테스트가 잡은 오류
원래 코드: 정수 변환 + 한 칸만 방문양수의 칸 경계 너머 적 누락
floor만 수정하고 한 칸만 방문음수 계산을 고쳐도 이웃 칸 누락은 남음
원래 코드로 음수 위치 검색0번 칸을 찾아 −1번 칸의 적 누락
floor + 주변 9칸 고정큰 반경의 적 누락

네 오답 조건 모두 차이를 검출했다. 로그의 DETECTED는 수정 코드가 실패했다는 뜻이 아니라, 의도한 오답을 잡았다는 뜻이다.

mismatch=0은 검사한 1,214개 조회에서 수정 코드의 ID 목록이 기준과 같았다는 뜻이다. 4/4는 일부러 넣은 네 가지 오답 조건을 모두 검출했다는 뜻이다.

두 결과를 함께 봐야 한다. 수정 코드가 통과했고, 원래 누락을 만드는 코드로 바꾸면 테스트가 실패를 알아챘다. 다만 이것이 모든 입력의 정확성이나 성능 향상까지 증명하지는 않는다.

무엇까지 확인한 것인가?

2026-10-15, Windows MSVC /utf-8 /O2 /W4 /EHsc /std:c++17로 경고 없이 빌드하고 실행했다. 일반 C++ 단일 Thread 테스트이며 Unreal Automation Test가 아니다.

테스트는 칸에 ID 목록을 저장하고 별도 Enemy 저장소에서 현재 상태를 읽는다. 본문의 Grid.At() 설명용 발췌와 저장 형태는 다르지만, floor → 사각형의 칸 범위 → 거리 제곱 판정이라는 검색 방식은 같다. 원과 칸의 겹침을 추가 검사하는 최적화는 구현하지 않았다.

검사한 것은 위 조건의 결과와 등록 일관성이다. 모든 부동소수점 입력의 수학적 정확성, 동시 접근, Unreal 객체 수명, 성능 향상을 증명한 것은 아니다. 유한한 좌표·음수가 아닌 반경과 정수 칸 번호의 안전 범위를 전제로 한다.
