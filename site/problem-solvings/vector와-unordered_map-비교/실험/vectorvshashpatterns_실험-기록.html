VectorVsHashPatterns_실험 기록

2026년 10월 15일

왜 이 실험을 더 했는가

앞선 실험에서 조회 목록을 늘리자 시간이 달라졌다. 하지만 그때는 목록의 메모리 크기와 조회 순서, 접근하는 키 수가 함께 달라졌다.

그래서 이번에는 둘로 나눴다.

기존 코드의 patterns 모드다. 기존 Compare/VectorLookup/MapLookup을 재사용했다. 단일 Thread, 7 samples, 중앙값, 실행 순서 교대다.

이번 후속 실험의 키는 1~N이다. 이전 본 실험의 분산된 정수 키와 다르므로, 이전 표와 절대 시간만 직접 비교하지 않는다. 이번 실험 안에서 통제한 조건끼리 비교한다.

A. 조회 목록이 같아도 순서가 영향을 줄까?

같은 키를 같은 횟수만큼 찾았는데도 시간이 달라졌다.

조회 수는 모두 65,536개다. int 목록의 데이터 크기는 256KiB이며, 컨테이너·찾는 키·키별 빈도를 유지했다.

성공/실패를 절반씩 섞은 입력도 따로 확인했다. 섞기와 정렬은 측정 밖이다.

8개 원소, seed 1, 혼합 조회:

순서vector · Run 1map · Run 1vector · Run 2map · Run 2
반복 패턴2.00 ns1.16 ns2.00 ns1.08 ns

세 경우의 평균 vector 비교는 6.295회, map equality는 1회로 같았다. 존재하지 않는 키까지 포함한 고유 조회 키도 16개로 같았다.

→ 원소 수·비교 횟수·목록 크기만으로 실행 시간을 설명할 수 없다. 데이터를 만나는 순서 자체도 영향을 준다.

이번 조건에서는 같은 키를 모으면 vector가 map보다 빠른 성공 조회도 있었다. 반대로 같은 multiset을 섞으면 map이 이기는 조건도 있었다. “8개면 vector” 같은 경계값으로 남기지 않는다.

그렇다면 Branch Prediction 때문이라고 확정할까?

아래 시간 측정만으로는 아니었다. 이후 VTune 후속 실험에서 8개 원소의 같은 혼합 조회를 두 번씩 수집했고, 순서를 섞으면 분기 실패와 CPI가 함께 증가했다. 이 작은 조건에서는 분기 예측을 원인으로 볼 측정 근거가 생겼다. 캐시 기여율이나 다른 규모까지 확인한 것은 아니다.

순서를 바꾸면 성공/실패 분기의 규칙성도 달라지고, 같은 후보를 얼마나 가까운 시점에 다시 읽는지도 달라진다. 분기 예측과 시간적 locality 모두 설명 후보다.

다만 이전보다 한 가지는 더 좁혀졌다.

목록의 메모리 크기를 늘리지 않아도 차이가 생겼다. 따라서 앞선 목록 길이 실험을 “목록이 커져 cache에 안 들어가서”만으로 설명하면 부족하다.

정렬된 조회 순서를 실제 게임에 곧바로 적용하라는 뜻도 아니다. 이 실험은 읽기와 합산이며, 처리 순서에 의미가 있는 시스템에서는 의미 보존을 먼저 확인해야 한다.

B. 목록 크기를 고정하고 찾는 키를 넓히면?

map에 저장된 원소 수는 50,000개로 유지했다. 조회 목록은 모두 65,536개다.

저장된 Enemy 중 일부 위치에서만 키를 고르게 하다가, 선택 가능한 키 범위를 전체로 넓혔다. 조회는 모두 성공이다.

50,000개 중 모든 키가 반드시 등장하는 목록은 아니다. 난수 선택 결과 36,548개를 실제로 조회했다.

→ 목록 자체의 메모리 크기가 같아도, 접근하는 후보 노드의 범위를 넓히면 조회 비용이 달라졌다. equality 횟수는 약 1.1회로 비슷했다.

그렇다고 비용이 키 수에 단조 증가하지는 않았다. 8개보다 64개에서 조금 더 짧았다. 키별 bucket 상태·빈도·실행 잡음까지 있으며 최적 키 수를 정한 실험이 아니다.

접근하는 키를 바꾸면 키 값과 후보 분포·재접근 패턴도 달라진다. 따라서 이 결과 역시 cache miss만 분리해 측정한 것은 아니다.

C. 일부 큰 값이 반복된 이유도 확인했다

전체 patterns 실행의 seed 2, 4,096개 일부 구간에서 vector 시간이 약 390 → 650ns, 혼합 조회는 약 590 → 1,000ns로 바뀌었다. 두 독립 실행에서 비슷한 변화가 보여 무시하지 않았다.

그 차이를 조회 순서의 효과로 곧바로 기록하지 않았다.

patterns-control 모드를 추가했다. 각 조건의 앞뒤에 항상 동일한 periodic 목록을 vector로 한 번 실행해 기준 시간을 남겼다.

기준 작업은 순서도 바꾸지 않는다. 그것까지 느려진다면 후보의 변화 전부를 순서에 귀속할 수 없다.

4,096개, seed 1, 혼합 조회의 Control Run 2:

후보 순서vectormap기준 전기준 후
반복 패턴586 ns1.75 ns586 ns584 ns
무작위로 섞음583 ns10.27 ns584 ns592 ns
같은 키끼리 모음584 ns1.25 ns594 ns619 ns

이 구간에서는 vector 시간과 기준 작업이 대체로 유지되는 동안 map의 순서 효과가 반복됐다.

다른 구간은 기준 자체도 바뀌었다. Control Run 2의 seed 2에서는 기준이 약 390ns에서 449ns로, 이후 혼합 기준도 약 650~720ns까지 변했다.

→ 실행 중 변화가 있는 구간의 vector 시간 차이는 순서 효과와 구분해서 보류한다. CPU 주파수·스케줄링·cache 상태를 직접 수집하지 않았으므로 기준 변동의 원인도 확정하지 않았다.

기준을 앞뒤로 한 번씩 실행했다고 환경을 완전히 통제한 것은 아니다. 측정 도중의 짧은 변동까지 모두 잡지는 못한다.

기록과 재현

41개 후속 조건을 두 번, 기준 대조 12개 조건을 두 번 실행했다. 기록된 checksum 불일치는 모두 0이었다.

  • 순서·키 범위 Run 2
  • 기준 대조 Run 1
  • 기준 대조 Run 2
  • 코드

학습 폴더 기준으로 재현/BuildVectorFactors.cmd로 만든 최적화 빌드를 실행한다.

앞의 두 patterns 기록은 기준 대조를 추가하기 전 빌드다. 공통 lookup/측정 함수는 그대로이고, 마지막 코드에서 각 모드를 다시 실행할 수 있다. 새 빌드의 동일한 절대 시간까지 보장하지 않는다.

이 patterns 비교 당시에는 Sampling Driver/관리자 권한 오류로 hardware event를 수집하지 못했다. 이후 실제 Windows 관리자 실행으로 수집 문제를 해결하고, 8개 원소의 periodic/shuffled 혼합 조회를 하드웨어 A/B 수집으로 확인했다. 나머지 규모·키 범위 조건은 아직 수집하지 않았다.
